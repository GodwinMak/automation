4) Least invasive tap-point for forwarding

Recommended tap-point:
- Immediately after successful current-state DB writes in each cron run, enqueue an event payload to a local non-blocking spool.
- This avoids extra SELECT queries and avoids network waits in the cron execution path.

Per-job practical tap locations:
- updateDIA: after bulk upsert of diacustomers, optionally also after key enrichment updates.
- updateIPT: after bulk upsert of iptcustomers.
- updateShared: after bulk upsert of sharedcustomers.
- updateL3VPN: after bulk upsert of l3vpncustomers.
- updateFTTH: after upsert + down-mark block completes.
- isisAdjacent: after per-device DB update cycle completes (prefer batched event payload, not per-row remote push).

5) Delivery mechanism options with tradeoffs

Option 1: Fire-and-forget async HTTP push from cron
- Pros:
  - Fast to implement.
  - Minimal architecture changes.
- Cons:
  - Still performs network and socket work in cron process.
  - Harder delivery guarantees.
  - Risk of noisy failures under network instability.

Option 2: Local durable queue/spool + separate forwarder worker (recommended)
- Pros:
  - Cron path does minimal local append and returns immediately.
  - Remote outages do not block/fail cron.
  - Retries/backoff happen outside cron process.
  - Good operational control (batch size, retry rate, backpressure).
- Cons:
  - Requires one additional worker process and local spool management.

Option 3: Pull-based scheduled batch export (delta reads)
- Pros:
  - Very low per-poll overhead.
  - No per-event remote call from cron path.
- Cons:
  - Adds periodic read load on production MySQL.
  - Requires robust watermark logic.
  - Can miss transient states if not captured in source history.

Option 4: MySQL binlog CDC/replication
- Pros:
  - Comprehensive change capture with low app code changes.
- Cons:
  - Higher operational complexity.
  - Requires binlog setup, retention, and CDC tooling.

6) Recommendation for your constraints

Best-fit recommendation:
- Use Option 2 (local durable spool + independent forwarder worker).

Reason this best matches your goals:
- Cron jobs never wait on remote warehouse network.
- Network hiccups cannot cause cron failure or retry storms in main process.
- CPU and memory overhead in cron remains near-zero.
- Retries/backoff are isolated in a dedicated worker.

7) Proposed implementation approach (safe, lowest overhead)

A) Producer side on production server
- Add a tiny enqueue utility called by cron jobs:
  - Accepts service_type, poll_timestamp, and payload array/object.
  - Appends NDJSON line(s) to local spool file.
  - Catches errors and logs warning only; never throws to cron flow.

B) Forwarder worker (separate process)
- Reads spool file in batches.
- Sends batches to remote ingest endpoint.
- Uses exponential backoff + jitter on failures.
- Tracks checkpoint/offset to avoid duplicates as much as possible.
- Writes health metrics/logs:
  - queued_count
  - send_success/send_fail
  - oldest_pending_age
  - backoff_seconds

C) Logging and safety
- Add explicit non-fatal logging in producer and forwarder.
- Ensure enqueue failures are visible but non-blocking.
- Enforce queue size cap and rollover policy to prevent disk growth.

8) Remote Ubuntu ingestion service design (minimal)

Option A: Node.js + Express ingest API (recommended)
- Endpoint:
  - POST /ingest/network-poll (batch payload)
- Responsibilities:
  - Validate auth token and payload schema.
  - Bulk insert into warehouse table(s).
  - Return ack with inserted count.

Warehouse storage choices:
- Table design A (simple): one wide event table with payload_json
  - Columns: id, service_type, poll_ts, source_host, record_key, payload_json, ingested_at
- Table design B (normalized): per-service history tables

Partitioning suggestion (MySQL):
- Partition by poll timestamp range (monthly partitions), e.g. RANGE on TO_DAYS(poll_ts).

Option B: File-drop + importer
- Accept gzipped NDJSON files by SFTP or mounted path.
- Separate importer loads to MySQL or writes Parquet/CSV.

9) ML-oriented export path
- Keep raw event history in warehouse MySQL.
- Run scheduled export job (hourly/daily) to produce Parquet/CSV by date/service.
- Store in object storage or local data lake path for model training pipelines.
