Model Structure and Databases Involved
Date: 2026-07-01

1) Databases Involved

A) Current Production Database (active in code)
- Engine: MySQL
- Host: localhost
- Database name: automation_db
- Config source: backend/Config/dbConfig.js (reads env vars)
- Env variables used:
  - DB_HOST
  - DB_USERNAME
  - DB_PASSWORD
  - DB_NAME

B) Proposed Historical Warehouse Database (recommended)
- Engine: MySQL (on separate remote Ubuntu server)
- Suggested database name: automation_warehouse (or any preferred name)
- Purpose:
  - Store historical snapshots/events from cron poll results
  - Power long-term reporting and ML exports

4) Important Relationships (from Models/index.js)

Service current-state to info
- diacustomers 1:N customerinfos (join key: interface)
- iptcustomers 1:N iptcustomerinfos (join key: interface)
- sharedcustomers 1:N sharedcustomerinfos (join key: interface)
- l3vpncustomers 1:N l3vpncustomerinfos (join key: interface)
- ftthcustomers 1:1 ftthcustomerinfos (join key: customerID)

Cross-domain links
- customerinfos / iptcustomerinfos / sharedcustomerinfos / l3vpncustomerinfos -> client_dbs
  - join via cid <-> network_cid

Device links
- devices 1:N switchConfiguration
- devices 1:N isisAdjacency

User links
- users 1:N notifications
- users 1:N favorites
- users 1:N push_tokens

5) Notes for historical forwarding design
- Current production DB is optimized for current state (upsert/update-heavy tables).
- Status transition history already exists for customer services.
- ISIS currently stores mutable latest state, not a dedicated append-only history table.
- For long-term analytics/ML, keep historical snapshots/events in a separate warehouse DB.
